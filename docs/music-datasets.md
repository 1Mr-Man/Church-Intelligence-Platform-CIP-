# Music Datasets (Phase 2.1)

This document explains how a local music dataset (a hymnal, a worship
set, a songbook) gets onto disk: the importer, the dataset file format,
validation, idempotency, versioning - and, first and most importantly,
the licensing policy that governs all of it. It mirrors
[`docs/bible-datasets.md`](bible-datasets.md) closely; where the two
differ, it's because a song/lyric dataset genuinely has a different
shape from a Bible translation, not because the discipline is different.

## Licensing policy - read this first

**CIP does not bulk-download or scrape song lyrics from the Internet,
does not bypass licensing restrictions, and does not ship a large
copyrighted song database merely because it is technically accessible.**
This is a hard constraint on the system, not just a guideline for this
phase - song lyrics are copyrighted content at least as often as Bible
translations are, frequently more restrictively licensed.

A music dataset may only be imported when one of the following is true:

- the user provides the data themselves,
- the data is public domain (many hymns are, having been written well
  over a century ago),
- the license explicitly permits the intended (local, offline) use, or
- the project has explicit distribution permission from the rights
  holder.

The importer has no network access at all (see "Offline" below), so it
cannot download anything even if asked to - but the policy holds even
for data a user supplies locally: nothing here validates *license
terms* (that requires human judgment), only *data shape*. When a
dataset's licensing metadata is not known, it is recorded as
`null`/`UNKNOWN` (see [`docs/content-registry.md`](content-registry.md))
rather than guessed.

### The development fixture is fictional, on purpose

`database/seeds/dev_seed.sql`'s music fixture (`music:dev-hymnbook`,
`music:dev-worship-set`, `music:dev-disabled-set`) uses entirely
invented song titles and lyrics - "Test Fixture Hymn One," "This is a
test hymn about steadfast care" - never real hymn or worship song text.
Public-domain hymn text was considered and would have been permissible,
but the fictional fixture sidesteps needing to make (and defend) a
copyright judgment call at all, which is the more conservative choice
this phase deliberately took.

## The importer

`cip_integrations_music::import_music_dataset(conn, dataset)` is a
reusable, local music dataset importer - the music-domain counterpart
to `integrations/bible::import_bible_dataset`. It is the *only* way the
`music_songs`/`music_aliases`/`music_sections`/`music_lyrics` tables are
populated outside the tiny development seed.

It never touches the filesystem and never accepts raw SQL - see
"Security" below.

### Dataset file format

A dataset is one JSON object, `MusicDatasetInput`:

```json
{
  "contentId": "music:dev-hymnbook",
  "name": "Test Fixture Hymnbook",
  "language": "en",
  "publisher": null,
  "copyright": null,
  "license": "public domain",
  "distribution": "public domain",
  "datasetVersion": "1.0",
  "songs": [
    {
      "id": "h1",
      "title": "Test Fixture Hymn One",
      "aliases": ["First Fixture Hymn"],
      "songType": "hymn",
      "language": "en",
      "number": "120",
      "author": null,
      "composer": null,
      "sections": [
        { "id": "h1-v1", "kind": "verse", "sequence": 0 }
      ],
      "lyrics": [
        { "sectionId": "h1-v1", "sequence": 0, "text": "This is a test hymn about steadfast care" },
        { "sectionId": "h1-v1", "sequence": 1, "text": "Every day I see new signs of faithful love" }
      ]
    }
  ]
}
```

`contentId` is the Content Registry id this dataset will be (or already
is) registered under, e.g. `"music:dev-hymnbook"` - provided by the
caller, following the same `"<type>:<domain-id>"` convention Phase 1.5
established, never generated by the importer.

`songType` must be one of `hymn`/`worship_song`/`chorus`/`gospel_song`/
`psalm`/`anthem`/`spiritual_song`/`other`; a section's `kind` must be
one of `verse`/`chorus`/`bridge`/`refrain`/`stanza`/`intro`/`outro`/
`other`. `aliases`/`number`/`author`/`composer`/`sections`/`lyrics` are
all optional (omitted or empty means genuinely absent, never guessed).
A lyric line's `sectionId` is nullable - a song this dataset didn't
structure into named sections still needs its lines storable; not every
real hymnal/songbook structures every song the same way.

The frontend's import UI reads the selected file as text with
`FileReader` and sends the raw JSON string to the `import_music_dataset`
Tauri command - the command never receives or opens a file path itself.

### Validation

Fatal (aborts the whole import, nothing is written):

- empty/missing `contentId`, `name`, `language`, or `datasetVersion`.

Per-song (that song is skipped and reported; every other valid song
still imports):

- empty/missing `id` or `title`,
- a `songType` that doesn't strictly parse to one of the eight known
  values,
- a duplicate song `id` within the same dataset.

Per-section (within an otherwise-valid song):

- empty/missing `id`, or a `kind` that doesn't strictly parse,
- a duplicate section `id` within the same song.

Per-lyric (within an otherwise-valid song):

- empty/whitespace-only `text`,
- a duplicate `sequence` within the same song,
- a `sectionId` that doesn't reference a section actually present
  earlier in the same song's `sections` array.

A duplicate alias is detected and reported (non-fatal) rather than
silently imported twice.

Nothing is silently repaired - an invalid row is reported with a
specific reason, never guessed into a "close enough" value.

### Idempotency

Every insert uses SQLite's `INSERT OR IGNORE`. Re-running the identical
import a second time inserts nothing new - every song/lyric line is
reported `alreadyPresent` instead of `imported`. This required one
schema addition beyond what a first draft had: `music_aliases` needed
an explicit `UNIQUE(content_id, song_id, normalized_alias)` constraint
so `INSERT OR IGNORE` actually has a conflict target to ignore against
- without it, a re-import would have silently duplicated alias rows on
every run. Proven directly:
`reimporting_the_identical_dataset_creates_no_duplicate_rows`
(`integrations/music/src/importer.rs`), which specifically asserts the
alias count stays at 1 after two imports.

**Never blindly overwriting existing content**: exactly the same rule
`integrations/bible`'s importer follows - if a song/lyric row already
exists, its content is left exactly as it is, even if a newer dataset
version has different text for it.

### The import report

Every import call returns a deterministic `ImportReport`:

```
contentId, datasetVersion, songsTotal, songsImported, songsAlreadyPresent,
songsInvalid, lyricLinesImported, lyricLinesAlreadyPresent, errors[], checksum
```

Every number is derived from the actual dataset and the database's own
state, never hard-coded.

### Checksum & dataset versioning

Each import computes a deterministic FNV-1a hash over the dataset's
content id/version and every song's id/title/sorted aliases/sorted
sections/sorted lyrics - identical content always produces the same
checksum regardless of input ordering, mirroring
`integrations/bible`'s checksum discipline exactly (same algorithm,
sort-before-hash, same reasoning). A dataset's identity is
`contentId` + `datasetVersion` + `checksum`, recorded in the Content
Registry.

## Dataset isolation - the core guarantee this phase adds

Every `MusicProvider` lookup is scoped by `contentId` - a song id or
number is never looked up without naming its dataset. This is proven
concretely, not just asserted: the dev-seed fixture deliberately gives
`music:dev-hymnbook`'s "Test Fixture Hymn One" and
`music:dev-worship-set`'s "Different Fixture Song Same Number" the
*same* song number (`"120"`), and
`integrations/music::tests::dataset_isolation_prevents_cross_dataset_lookup`
confirms searching one dataset for number `"120"` never returns the
other dataset's song.

## Local music search

`cip_core_music::search_songs(provider, content_ids, query, thresholds)`
is the deterministic dispatcher - see
[`docs/music-intelligence.md`](music-intelligence.md#deterministic-matching-coremusicmatcher)
for the full ranking/confidence model. Unlike `search_bible`, which
free-text-parses one query string, `search_music`'s `MusicQuery` is an
explicit shape (`Title`/`Number`/`Lyric`/`LyricSequence`) chosen by the
caller - the Tauri `search_music` command takes an explicit
`queryType`, and `MusicIntelligenceEngine`'s automatic transcript
dispatch (documented in `docs/music-intelligence.md`) tries them in a
fixed, deterministic order.

## Offline

The importer and matcher add no new dependency with any network
capability - verified structurally via `cargo tree -p cip-core-music`
and `cargo tree -p cip-integrations-music` (no `reqwest`/`hyper`/`ureq`/
`tungstenite` anywhere in either dependency graph), the same proof every
earlier phase established for its own domain.

## Security

- Never executes an imported file.
- Never trusts an arbitrary filesystem path - the backend command
  (`import_music_dataset`) takes JSON *text*, not a path; the frontend
  reads the file client-side.
- Never accepts SQL from a dataset file - every value is bound through
  `rusqlite` parameters, never string-interpolated into a query.
- Never silently overwrites an existing dataset (see "Idempotency"
  above).
- Never downloads unverified song content - there is no code path that
  fetches a dataset from the network at all.

## What's actually installed

In this development environment, the only installed content is the
tiny `database/seeds/dev_seed.sql` fixture: three datasets
(`music:dev-hymnbook`, `music:dev-worship-set` - both enabled;
`music:dev-disabled-set` - disabled, specifically so "a disabled
dataset is never searched" has something real to prove against), five
songs total, six lyric lines, one alias, all fictional. No real hymnal
or worship set has been imported or is claimed to be installed - the
importer, matcher, and `MusicIntelligenceEngine` are validated against
both this real fixture and a larger synthetic dataset built purely for
performance measurement (see
[`docs/music-intelligence.md`](music-intelligence.md#performance)) -
never against invented "real" song content.
